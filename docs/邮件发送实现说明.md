# 邮件发送实现说明

本文档说明当前仓库中“发送邮件”能力的实际实现方式、调用链路、运行配置与已知限制。

## 当前结论

- 当前生产发送通道是 Cloudflare Email Sending REST API。
- 通用邮件入口是 `POST /api/email/send`。
- 认证验证码邮件不经过上述 API 路由，而是在 better-auth 的 `emailOTP` 插件回调中直接调用发送工具。
- `server/utils/resend.ts` 文件名仍沿用历史命名，但其内部实现已经不是 Resend，而是 Cloudflare 邮件发送接口。
- 代码库中仍能看到 `RESEND_API_KEY` 文案和环境变量示例，它们当前不参与实际发送流程，属于遗留配置。

## 相关文件

- `server/api/email/send.post.ts`
  - 通用邮件发送 API。
  - 负责入参校验、限流、验证码模板拼装、调用底层发送器。
- `server/utils/auth.ts`
  - better-auth 初始化入口。
  - `emailOTP` 插件的 `sendVerificationOTP` 会直接发送登录/注册、邮箱验证、改邮箱、找回密码等验证码邮件。
- `server/utils/resend.ts`
  - 底层邮件发送器。
  - 负责开发模式控制台输出、Cloudflare API 请求、错误处理与投递结果检查。
- `nuxt.config.ts`
  - 注入运行时配置：发件人、Cloudflare 账号与 Token、开发模式邮件开关。

## 发送链路

### 1. 通用邮件 API

入口：`server/api/email/send.post.ts`

请求体支持以下字段：

```json
{
  "to": "user@example.com",
  "subject": "邮件标题",
  "text": "纯文本内容",
  "html": "<p>HTML 内容</p>",
  "template": "verify-code",
  "code": "123456",
  "expiresInMinutes": 10
}
```

规则如下：

- `to` 必填。
- `subject` 在普通邮件场景下必填。
- `text` 和 `html` 至少提供一个。
- 当 `template` 为 `verify-code` 时：
  - `code` 必须是 4 到 8 位数字。
  - `subject`、`text`、`html` 会被服务端验证码模板覆盖。
  - `expiresInMinutes` 会被限制在 1 到 30 分钟之间，默认 10 分钟。

该接口当前返回：

```json
{
  "success": true,
  "provider": "cloudflare-email",
  "to": "user@example.com",
  "template": "verify-code",
  "timestamp": "2026-07-29T00:00:00.000Z"
}
```

### 2. 认证验证码邮件

入口：`server/utils/auth.ts`

better-auth 的 `emailOTP` 插件开启后，以下验证码场景会走 `sendVerificationOTP`：

- `sign-in`
- `email-verification`
- `change-email`
- `forget-password`

处理流程：

- 根据 OTP 构建验证码邮件模板。
- 根据 `type` 生成邮件标题后缀，如“登录/注册”“邮箱验证”等。
- 直接调用 `sendEmail(...)` 发送，不经过 `/api/email/send`。

这意味着当前仓库里有两条邮件入口：

- 面向业务调用的 `/api/email/send`
- 面向认证系统的 `emailOTP.sendVerificationOTP`

## 底层发送器实现

入口：`server/utils/resend.ts`

### 开发模式行为

当运行时配置 `devConsoleEmail === 'true'` 时：

- 不实际请求 Cloudflare。
- 直接把收件人、发件人、主题和正文打印到控制台。

这适合本地联调登录/注册流程时避免真实发信。

### 生产发送行为

发送器会校验以下配置是否存在：

- `cfAccountId`
- `cfApiToken`
- `from`
- 邮件正文 `text` 或 `html`

随后向以下 Cloudflare REST 接口发起请求：

```text
POST https://api.cloudflare.com/client/v4/accounts/{cfAccountId}/email/sending/send
```

请求体结构：

- `from`: 支持仅地址，或 `{ address, name }`
- `to`: 当前实现固定为单收件人数组
- `subject`
- `text` 或 `html`

发送完成后：

- 若 HTTP 状态码非 2xx，抛出 Cloudflare API 错误。
- 若 Cloudflare 返回 `success: false`，拼接错误码与消息抛出。
- 若结果中存在 `permanent_bounces`，视为失败并抛错。
- 否则打印投递结果日志。

## 限流策略

仅 `/api/email/send` 实现了内存级限流。

参数：

- 窗口：10 分钟
- 同一 IP 最多 15 次
- 同一邮箱最多 5 次

实现细节：

- 使用 `globalThis.__emailRateLimitStore` 保存 `Map<string, number[]>`。
- 仅在当前 Worker 实例内生效。
- 不跨实例共享，不具备分布式一致性。

这意味着在 Cloudflare Workers 多实例或冷启动场景下，限流是“尽力而为”的本地保护，而不是严格全局限流。

另外，better-auth 的 OTP 发送链路没有复用这套 `/api/email/send` 限流逻辑；它主要依赖 `emailOTP` 插件自身的 `allowedAttempts: 5` 和 `expiresIn: 600` 配置控制尝试次数与有效期。

## 运行时配置

当前实现实际依赖以下运行时配置项：

```ini
DEV_CONSOLE_EMAIL=true
CLOUDFLARE_ACCOUNT_ID=your_account_id
CF_API_TOKEN_SEND_EMAIL=your_cloudflare_email_token
```

`nuxt.config.ts` 中还写死了默认发件人：

- `email.from = 'no-reply@orange-trees.com'`
- `email.fromName = 'SP飞行棋-大富翁版'`

better-auth 还依赖：

- `BETTER_AUTH_SECRET`
- `BETTER_AUTH_URL`

## 现状与注意事项

### 1. 命名与实现不一致

- `server/utils/resend.ts` 文件名仍指向旧供应商语义。
- README 中旧的 Resend 描述如果不更新，容易误导维护者。

### 2. 文档与配置示例存在遗留项

- `RESEND_API_KEY` 仍出现在部分文档或环境变量示例中。
- 当前运行时并未从 `nuxt.config.ts` 读取该值。

### 3. 限流覆盖面不一致

- `/api/email/send` 有本地内存限流。
- better-auth 的 OTP 直发链路没有复用同一套限流存储。

### 4. 模板存在重复

- `server/api/email/send.post.ts` 和 `server/utils/auth.ts` 都各自维护了一份验证码邮件模板。
- 两者视觉结构接近，但不是同一份共享模板函数。

## 建议的后续整理方向

如果后续要继续维护这块功能，优先级建议如下：

1. 将 `server/utils/resend.ts` 重命名为更准确的 `email.ts` 或 `cloudflare-email.ts`。
2. 抽出统一的验证码模板生成器，避免 API 路由与认证插件模板分叉。
3. 明确保留或删除 `RESEND_API_KEY` 遗留配置，减少环境变量噪音。
4. 如果需要更强限流一致性，将限流状态迁移到 KV、D1 或 Durable Object。
